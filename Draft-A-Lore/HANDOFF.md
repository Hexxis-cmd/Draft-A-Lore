# Draft A Lore — Handoff

Working notes for whoever continues this work. The app stays labeled **v1.0.0** through every iteration.
Treat committed documentation as possibly stale and verify against `src/` before writing anything.

## Ground rules for this codebase

- `src/` is the only place to edit app code: `core.js`, `views.js`, `story-tools.js`, `adventure-tools.js`,
  `styles.css`. `dist/` and `www/` are generated by `build.py` / `build-mobile.py` and are gitignored.
- Zero runtime dependencies and no network calls, with one exception: the optional Google Fonts catalog in
  `core.js`, loaded only when `navigator.onLine` is true. Charts must be hand-built SVG or canvas.
- Vanilla browser JS on the `DAL` namespace, no modules, no framework. Event handling is delegated through
  `data-action` attributes; never rename or remove an existing action value.
- All user data lives in browser storage under the `draftALore` key. Every new state field must default
  safely when absent so existing users' saved work is never broken. Migrate additively.
- Use design tokens (`var(--c-*)`, `var(--radius-*)`, `var(--ts-*)`, `var(--tap)`). Never hardcode colors in
  component CSS — every element must work in all themes.
- Touch targets stay at `var(--tap)` minimum inside the coarse-pointer and phone media queries, and touch
  text inputs use 16px to avoid iOS focus zoom.
- Comments explain non-obvious logic only. No development-process notes, no other products by name.

### Environment gotcha: binary assets

In the Perplexity project file repo, binary files (icons, logos, APK) arrive as Git LFS pointer stubs. If a
file's first line is `version https://git-lfs.github.com/spec/v1`, it is a placeholder, not an image.
Hydrate before building or moving:

```bash
pplx project files hydrate-lfs <path>...
```

`hydrate-lfs` refuses paths that have uncommitted changes, so hydrate **before** moving or renaming assets.
Persist work with `pplx project files submit -m "<message>"`; nothing survives the session otherwise.

## Phase 2, package 1 — Dashboard customization

An "Organize Dashboard" mode the user toggles in and out of, like a personalize-your-workspace mode.

- Cards get stable string ids. In organize mode each card exposes: move up / move down (drag-and-drop
  optional on top, buttons are the required baseline), hide/show, width half or full on the two-column
  grid, and height normal or tall for data-heavy cards only.
- Hidden cards appear in a "Hidden cards" area while organizing so they can be restored; outside organize
  mode they do not render at all.
- Persist as `dashboardLayout: { order: [], hidden: [], size: { <cardId>: { w:'half'|'full', h:'normal'|'tall' } } }`.
  Missing or partial state falls back to defaults, unknown ids in saved state are ignored, and cards added
  in future versions still appear when saved order predates them.
- Phones render every card full width regardless of saved width; organize mode must stay usable there.
- Outside organize mode no control affordances may remain visible.

## Phase 2, package 2 — Analytics overhaul

Two hand-built inline SVG visualizations, theme-aware through CSS custom properties:

1. **Word output bar graph** — words written per bucket, with range filters for 7 days, 30 days, 12 weeks
   and 12 months (daily buckets for short ranges, weekly/monthly for long ones). Shows total words in range
   and daily average. Needs axis labels, a baseline, value labels or hover/tap tooltips, a calm empty state,
   and an accessible label per bar carrying date and count.
2. **12-week activity heatmap** — one column per week, one cell per day, intensity by words written that
   day using the accent color at graded opacity, with weekday labels, month markers, a legend, and an
   accessible label per cell.

**Data correctness must be fixed as part of this.** Today the daily history stores cumulative totals rather
than words written that day, and daily/weekly/monthly goal progress is computed from lifetime total words,
so goals fill in permanently instead of resetting. Store a per-day delta keyed by local date `YYYY-MM-DD`,
derive every goal period from those deltas, migrate existing cumulative snapshots additively rather than
discarding them, and keep the streak consistent with the new data.

Also restyle, without removing: the existing daily/weekly/monthly/6-month/yearly goals, the global word
count tracker, and the streak flame. Cleaner type scale, spacing, progress bars, aligned numbers.

Explicitly excluded by the owner: habit-streak card, academy/learning card, reading room card, music or
playlist card, upcoming writing sprints card.

## Phase 2, package 3 — Project Goals card

Per-project target word count plus optional deadline, stored on the project object rather than global
state. Shows progress toward target, words remaining, and when a deadline exists the days remaining and the
words-per-day pace needed. Active goals are separated from completed ones; a goal completes when the target
is met.

## Phase 2, package 4 — Story Graph: grab mode, zoom, drag

Current behavior: zoom in / zoom out / reset buttons render in the canvas toolbar but have **no handlers**,
so they do nothing. Node dragging is implemented but does not move nodes in practice — confirmed broken by
the owner and by a browser test where three synthetic drag sequences left the inline `left`/`top`
unchanged with no JavaScript errors. Find the root cause before changing anything.

The owner's requested design, which should be implemented as its own feature:

- A hand/grab button in the canvas toolbar next to the zoom controls. Click or tap enters grab mode; click
  or tap again exits. A persistent mode, not a hold-to-pan gesture, so mouse, trackpad and touch behave
  identically. Show state with active styling, `aria-pressed`, and a tooltip. Escape exits.
- In grab mode, dragging anywhere pans the canvas and node dragging is suppressed; the cursor is
  grab/grabbing on pointer devices. Out of grab mode, dragging a node moves it and empty canvas does not
  pan.
- Clicking a node still selects it and opens the scene editor in both modes. Use a small movement threshold
  so a click is never swallowed by drag or pan logic.
- Zoom steps through clamped levels (roughly 0.4x to 2x) keeping the view centered, reset returns to 100%
  at origin or fits all nodes, and the current zoom level is displayed.
- Divide pointer movement by the current scale for both dragging and panning, or nodes drift from the
  cursor at non-100% zoom. Connection lines must stay attached while zooming, panning and dragging.
- Persist zoom and pan per project with safe defaults (absent means 100% at origin). Grab mode itself is
  transient and not persisted.
- On phones the button obeys `var(--tap)` sizing and panning must not fight page scrolling — use
  `touch-action` on the canvas rather than blocking scrolling globally.

## The RPG systems are now real

The owner's original concern was that stats, traits, items and inventory existed as data the rest of the
app ignored. That work is done. All rules live in one place, `src/rpg-engine.js`, on the `DAL.rpg`
namespace: a DOM-free, storage-free module that the Playthrough tool, the authoring UI and the exported
game all call. Nothing else in the app decides what a condition means.

What it holds:

- **One runtime state object** — stats, traits, inventory counts, equipped items by slot, flags, visit
  counts, current scene, ending, step number and a per-step change log.
- **Conditions** on stats (six comparisons), traits, item possession and quantity, a specific item being
  worn, a gear slot being filled or empty, flags, and scenes already visited — combined with all-of or
  any-of. The editor builds every picker from the project's real stats, traits, items, scenes and flags, so
  a typo cannot silently disable a choice. A stored value that no longer exists stays selected and is
  marked "— missing" rather than vanishing.
- **Effects** that set, raise or lower a stat with clamping to its minimum and maximum, grant, remove or
  flip a trait, give or take items respecting stack limits, equip and unequip (unequipping automatically
  when the item is lost), set or clear flags, redirect to another scene, and end the run as an ending or a
  failure. Entry effects and choice effects run in a fixed order, and every row shows in plain language
  what it will do.
- **Playthrough feedback** — stat bars with the amount each value moved, traits, inventory with a working
  equip control, equipped slots, flags, step and visit counts, a "What just changed" list after each
  choice, and locked choices that name the requirement they are waiting for. Whether unmet choices are
  shown locked or hidden is a story-wide setting in the Playthrough toolbar, overridable per choice.
- **Run-ending rules and endings** — a rule table in Stats & Traits watches one stat and stops the run with
  the author's own title and closing line; scenes can be marked as endings with an ending name; the closing
  screen distinguishes an ending, a failure and a scene that simply has no way out.
- **A story checkup** (`DAL.rpg.audit`, opened from the Story Graph toolbar) that reports unreachable
  scenes, choices that lead nowhere or to deleted scenes, requirements that can never be satisfied, and
  every reference to a stat, trait, item, flag or scene that no longer exists. It reports; it never repairs.
- **Export parity** — the playable HTML embeds the engine verbatim via `DAL.rpg.engineSource()`, so the
  download plays by the same rules as the Playthrough tool. The Twine export writes SugarCube variables,
  setters and gated links for everything expressible there and lists what it could not carry in a
  "Not Carried Over" passage.

`RPG.API` names every function serialised into an export; `audit` is deliberately excluded because it is an
authoring tool, not a runtime rule. `qa`-style engine checks are not committed, but the engine is written to
be testable without a browser: stub `DAL = {}`, evaluate `src/rpg-engine.js`, and call into `DAL.rpg`.

Still open in this area, for whoever picks it up next:

- Slots are a fixed list (`head`, `body`, `weapon`, `accessory`); author-defined slots would need a UI.
- Conditions cannot compare two stats to each other, and effects cannot copy one stat into another.
- The Twine export does not attempt gear slots, stack limits, clamping, run-ending rules or visit counts.
- Boolean stats still overlap with yes/no traits, as noted below.
